# Content SDK Multisite Basics

Site resolution from request (e.g. hostname or cookie); sites.json and proxy chain must stay consistent.

## When to Use

- User asks about multiple sites, hostnames, or site resolution.
- Task involves .sitecore/sites.json, multisite config, or proxy/middleware for site.
- User mentions "multisite," "site resolution," "hostname," or "sites.json."

## Hard Rules

- Site list is in `.sitecore/sites.json` (typically generated by Sitecore CLI or deployment). Avoid hand-editing unless the format is known; prefer CLI or config-driven generation.
- **App Router:** Middleware chain order is fixed: LocaleProxy → AppRouterMultisiteProxy → RedirectsProxy → PersonalizeProxy. Multisite proxy rewrites to /[site]/[locale]/...path; uses sitecore.config.ts multisite and api.edge.
- **Pages Router:** defineProxy(multisite, redirects, personalize). MultisiteProxy resolves site from request (hostname or cookie), rewrites; use skip and matcher to exclude API, _next, static files.
- Config: sitecore.config.ts → multisite (e.g. enabled, useCookieResolution). Do not change proxy order to fix site issues; fix config or sites.json instead.
- Single SitecoreClient; pass resolved site (and locale) from route/context into getPage, getDictionary, etc.

## Stop Conditions

- Stop if the user wants to reorder the proxy chain; explain that order is required (e.g. locale before multisite for App Router).
- Stop if sites.json format is unknown and the change could break resolution; suggest checking SDK docs or CLI output.
- Do not add a second site resolution mechanism (e.g. duplicate middleware); use the existing proxy and config.
