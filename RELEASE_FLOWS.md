# Release Flows Guide

## Overview

This repository uses a PR-based release workflow with three release types:
- **Canary Releases**: Automatic on every push to `dev` (no PR needed)
- **Full Stable Releases**: PR-based from release branch → `dev` (requires `(release)` prefix)
- **Patch Releases**: PR-based from release branch created from tag (requires `(release)` prefix)

**Key Principle**: All stable releases require a PR with `(release)` prefix in the title. Versions are bumped BEFORE merge, then published using `lerna publish from-package`.

---

## Release Types Summary

| Release Type | Trigger | Source Branch | Target Branch | Version Format | Tools |
|--------------|---------|---------------|---------------|----------------|-------|
| **Canary** | Push to `dev` | `dev` | N/A (direct push) | `1.4.0-canary.3` | Lerna |
| **Full Stable** | Merge PR with `(release)` prefix | `release/1.4.0` | `dev` | `1.4.0` | Beachball + Lerna |
| **Patch** | Merge PR with `(release)` prefix | `release/1.3.x` | `release/1.3.x` (self-merge) | `1.3.1` | Beachball + Lerna |

## Detailed Release Flows

### 1. Canary Release

**When**: Every push to `dev` branch (without `(release)` prefix)

**Steps**:
1. Make changes
2. Push to `dev` branch

**Automated** (via `publish.yml`):
- Build packages
- Generate API docs
- Bump versions: `lerna version prerelease --preid canary`
- Publish to npm: `lerna publish --canary`

**Result**: Packages published as `1.4.0-canary.3` format

---

### 2. Full Stable Release

**When**: Ready to release a new version (e.g., `1.4.0`)

**Steps**:
1. Create release branch from `dev`: `git checkout -b release/1.4.0`
2. Make final changes (if any)
3. Create change files: `yarn beachball change` (select minor/major)
4. Bump versions: `yarn bump` (updates versions & generates changelogs)
5. Commit version bumps and changelogs
6. Create PR: `release/1.4.0` → `dev` with title `(release) Release version 1.4.0`
7. Merge PR

**Automated** (via `publish.yml`):
- Detects `(release)` prefix in merge commit message
- Build packages
- Publish stable packages: `lerna publish from-package` (reads already-bumped versions)
- Generate API docs

**Result**: Packages published as `1.4.0` (stable)

**Note**: GitHub must be configured to use PR title as merge commit message: Settings → Pull Requests → "Allow merge commits" → Change "Default commit message" dropdown to "Pull request title"

---

### 3. Patch Release

**When**: Need to patch an existing version (e.g., `1.3.0` → `1.3.1`)

**Branch Creation** (choose one):

**Option A: Automated (Recommended)**
1. Go to **Actions** → **Prepare Release Branch** → **Run workflow**
2. Fill inputs:
   - Version pattern: `1.3.x`
   - Release type: `patch`
   - Base tag: `v1.3.0`
3. Workflow creates `release/1.3.x` branch from tag

**Option B: Manual (Fallback)**
1. `git checkout v1.3.0`
2. `git checkout -b release/1.3.x`
3. `git push -u origin release/1.3.x`

**Remaining Steps** (same for both options):
1. Checkout branch: `git checkout release/1.3.x`
2. Make patch changes
3. Create change files: `yarn beachball change` (select patch)
4. Bump versions: `yarn bump` (or prep-release workflow can auto-bump if change files exist)
5. Commit version bumps and changelogs
6. Create PR: `release/1.3.x` → `release/1.3.x` with title `(release) Patch release 1.3.1`
7. Merge PR

**Automated** (via `publish.yml`):
- Detects `(release)` prefix in merge commit message
- Build packages
- Publish patch: `lerna publish from-package` (reads already-bumped versions)
- Generate API docs

**Result**: Packages published as `1.3.1` (patch)

## Technical Details

### Version Bumping

| Release Type | When | Tool | Command |
|--------------|------|------|---------|
| Canary | During publish workflow | Lerna | `lerna version prerelease --preid canary` |
| Full Stable | Before PR merge | Beachball | `yarn bump` (or `beachball bump`) |
| Patch | Before PR merge | Beachball | `yarn bump` (or `beachball bump`) |

### Changelog Generation

- **Generated by**: Beachball during `beachball bump`
- **Format**: `[@package-name] Description ([commit-hash](link))`
- **Location**: `packages/*/CHANGELOG.md`
- **Features**: Includes commit links, grouped changelogs for dependent packages

### npm Publishing

- **Tool**: Lerna (`lerna publish from-package`)
- **Why**: Reads existing `package.json` versions (already bumped), prevents double bumping
- **Canary**: `lerna publish --canary` (creates canary versions)
- **Stable/Patch**: `lerna publish from-package` (publishes already-bumped versions)

### Workflow Logic

| Condition | Branch | Action | Workflow |
|-----------|--------|--------|----------|
| Push to `dev` + no `(release)` prefix | `dev` | Create canary release | `publish.yml` |
| Push to `dev` + `(release)` prefix | `dev` | Publish stable packages | `publish.yml` |
| Push to `release/**` + `(release)` prefix | `release/**` | Publish stable packages | `publish.yml` |
| Push to `release/**` + no `(release)` prefix | `release/**` | No action (skips publish) | `publish.yml` |

---

## Important Notes

1. **PR Title Format**: Must contain `(release)` prefix (e.g., `(release) Release version 1.4.0`)
2. **Version Bumping**: Done BEFORE merge, NOT during publish
3. **Double Bump Prevention**: Uses `lerna publish from-package` to read existing versions
4. **Merge Commit Message**: GitHub must be configured: Settings → Pull Requests → "Allow merge commits" → "Default commit message" = "Pull request title"
5. **Change Files**: Required for stable/patch releases (created with `yarn beachball change`)
6. **Canary Releases**: Automatic, no change files needed
7. **API Docs**: Auto-generated for all release types

## Troubleshooting

**Release didn't trigger?**
- ✅ Check PR title contains `(release)` prefix
- ✅ Check PR was merged (not just closed)
- ✅ Check GitHub Actions logs for errors
- ✅ Verify merge commit message contains `(release)` prefix

**Versions not bumped?**
- Run `yarn bump` before merging PR
- Or let prep-release workflow auto-bump if change files exist

**Changelogs not generated?**
- Ensure `yarn bump` was run (generates changelogs automatically)
- Check `packages/*/CHANGELOG.md` files
